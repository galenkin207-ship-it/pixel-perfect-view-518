- Деплой staging: push в `staging` (GitHub Actions, `deploy-staging.yml` существует
  ТОЛЬКО в ветке `staging` — не делать вывод об отсутствии staging CI по main-ветке)

## КРИТИЧНО: безопасность веток

- **Перед ЛЮБЫМИ изменениями** — проверить текущую ветку (`git branch --show-current`).
  Часто после мержа остаёшься на `main` — это частая причина случайных коммитов не туда.
- `git pull --rebase origin main` НЕ переключает ветку. Всегда явный
  `git checkout <branch>` перед любой работой.
- **Ветка по умолчанию для новой работы — `staging`**, если Константин явно не
  подтвердил, что staging проверен, и не попросил смержить в main
  (фраза вида «мержим в main»).
- Без явного подтверждения — никогда не пушить и не мержить в `main`.

## Порядок работы (staging-first)

1. `git checkout staging`
2. `git pull --rebase origin staging`
3. Внести изменения
4. Проверить: `npx tsc --noEmit` (существующие ошибки в роуте brigades из-за
   отсутствующего сгенерированного route tree — ожидаемы и не относятся к делу,
   не блокируют), затем `npm run build`
5. `git add -A` → `git status` (проверить, что попадает в коммит, ДО commit)
6. Коммит с понятным сообщением
7. `git push origin staging`
8. Дать ссылку на статус деплоя:
   https://github.com/galenkin207-ship-it/pixel-perfect-view-518/actions
9. Ждать явного подтверждения от Константина, что staging протестирован,
   прежде чем предлагать мерж в main
